# 학습 해설 작성 기준

revision: SYNC-2026-11-17-LEARN-REPAIR-01. 원본 godieor-app/docs/system/learning-policy.md.

2026-11-17 사용자 시정 요청: 작업하면서 기술을 어떻게 선택했고 문제를 어떻게 해결했는지 읽으며 함께 성장할 수 있어야 한다. 작업·검증 경과를 압축한 메모를 학습 해설로 대신하지 않는다.

## 독자와 글의 목적

독자는 작업 대화·작업 ID를 모르는 개발자다. 한 글은 하나의 기술 질문을 다룬다. 첫 문단은 구체적인 문제와 배울 원리로 시작한다. 낯선 용어는 첫 사용 때 설명한다. 원본 링크는 주장을 확인하는 근거이며 본문 이해의 선행 과제가 아니다.

기술 해설은 문제 → 원인·원리 → 작은 예제 → 대안과 제약 → 선택 이유 → 적용·확인 → 비용·재검토 조건을 연결한다. 제목·표·코드·그림은 이해에 도움이 될 때 사용한다. 분량·절 개수·테스트 개수는 품질 기준이 아니다.

## 쓰기 전과 쓴 뒤

1. 관련 ADR·작업 기록·코드를 읽고 설명할 기술 질문을 고른다. 원본에 없는 당시 선택 이유는 사후에 지어내지 않는다. 사후 대안 비교는 그렇게 밝힌다.
2. 작은 입력·출력 또는 요청 순서로 문제가 생기는 이유와 수정 원리를 설명한다. 실코드·실제 재현·가상 예제·의사코드를 구분한다.
3. 대안의 장단점을 실제 제품 제약에 연결한다. 선택한 기술 이름과 검사 수만 적은 글은 해설로 완료 처리하지 않는다.
4. 본문에서 작업 ID·로그·SHA를 빼고 읽어도 “왜 이 선택을 했고 어떤 조건에서 바꾸는가”에 답할 수 있는지 확인한다. 구체적 반례로 설명할 수 없으면 추가 조사하거나 재작성 필요로 남긴다.
5. 이전 주장에 영향을 주는 변경은 해당 설명을 다시 편집한다. 새 기술 질문은 글을 나눈다. 날짜별 작업 결과를 계속 덧붙여 여러 주제를 한 글에 쌓지 않는다.

## 기록의 역할

- 작업 카드·ADR: 실제 실행 명령·결정·실패·관측·후속 과제의 원본.
- verifier/docs/learning: 위 원본을 바탕으로 독자에게 설명하는 통합 기술 해설. app/backend에도 원본을 찾는 안내를 둔다.
- verifier run·review: 독립 검증 근거. 해설 작성자가 승인 결과를 대신 만들지 않는다.

실제 장애·개발 중 재현·예방 설계를 구분한다. 현재 결과와 과거 시점을 혼동하지 않는다. 사용자 이해도·본인의 경험·측정하지 않은 성과를 대신 작성하지 않는다. 면접·블로그 전환은 읽을 수 있는 기술 해설을 만든 뒤 필요할 때 수행한다.

## 기존 글 복구

학습 카탈로그에서 재작성 여부와 남은 문제를 표시한다. 기존 관측은 Git 이력이나 별도 archive로 보존하고 본문의 날짜별 append를 대체한다. 보관된 글은 현재 정책·신규 실행 결과의 원본으로 쓰지 않는다. 재작성 완료는 문서 편집 상태이며 기술 내용의 독립 검증 완료를 뜻하지 않는다.
