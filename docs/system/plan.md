# GODIEOR · 데이터 우선 기본기능 완성 계획

- revision: `SYNC-2026-11-17-04`.
- 원본 app/docs/system/plan.md. backend/verifier 사본을 함께 갱신한다.
- 2026-11-17 사용자 확정: 목표는 기본기능 완성. **데이터 수집·적재 완료 → 배포 환경 설정·실제 배포 → 나머지 기본기능 완료 → 디테일·디자인** 순서로 진행한다.
- 이전 계획의 ‘앱 기능을 먼저 끝내고 배포를 마지막에 연결’하는 순서를 대체한다. 과거 관측·계획은 Git 이력 및 작업 카드에 보존한다.

## 단계와 현재 위치

| 순서 | 작업 | 현재 상태 | 다음 단계 진입 조건 |
|---|---|---|---|
| 1 | 데이터 수집·검토·적재·갱신 | 진행 중 | 아래 데이터 완료 조건 충족. 적재 건수·자체 테스트 수만으로100% 처리하지 않음 |

| 3 | 나머지 기본기능 완성 | 일부 구현 있음, 집중 작업은 배포 후 | 실제 배포 환경과 iPhone에서 핵심 사용 흐름·실패/복원 경로 확인 |

## 1단계 · 데이터 수집·적재 완료 조건

대상 분야·국가·기간·플랫폼은 docs/product.md와 후속 사용자 확정 범위를 따른다. 극장 영화, 4대 OTT의 영화/시리즈/예능/다큐/애니, 게임, EPL을 임의로 빼서100%라고 하지 않는다. 조회 범위와 실제 수집 가능 범위는 별도로 기록한다. 모든 사이트·전 세계 모든 작품을 전수 확보했다고 약속하는 지표가 아니다.

- [x] 원천별 수집 대상·기간·페이지·지원 범위와 알려진 누락/미지원 경로를 한 표로 고정한다. 현재 두 달 discovery와 제품의2026년 이후 조회 범위를 같은 것으로 세지 않는다.
- [ ] 기존 검토본 재게시뿐 아니라 새 작품/새 시즌의 독립 발견→정체성·국가·플랫폼·정확한 최초일 확인→고정 키 생성→DB→API까지 실제 새 입력으로 검증한다. 가상 입력 성공이나 수동23건 적재를 일반 자동 신규 게시 성공으로 세지 않는다.
- [ ] 정상적으로 확인 가능한 입력의 반영을 매번 수동 작품별 적재로 대신하지 않는다. 근거 불충분한 입력의 명시적 검토 대기는 지원하되, 이미 발표된 정확한 공식 일자를 놓치는 경로는 미완료로 남긴다.
- [ ] 각 분야 실제 DB/API 값과 독립 근거를 대조하고, 국가·플랫폼·시즌별 이벤트·date_only/instant/미정·중복 방지·기존ID/이력을 확인한다.
- [ ] 일일 수집·원천 재확인·날짜 변경 감지/검토 후 갱신·실패 격리·재시도/복구·마지막 성공 상태를 실제 실행으로 확인한다. API 제공처 미등재는 대체 공식 원천 등 처리 경로를 검증하고 필수 범위 미수집을 성공에 숨기지 않는다.
- [ ] 알려진 필수 수집/적재 결함을 해결하고 개발 검증 결과를 남긴다. StreamPick 개수 일치만을 완료 기준으로 복구하지 않으며, 이미 확인한 문제를 목록에서 지워100%로 만들지도 않는다.

날짜가 아직 발표되지 않은 작품을 정확한 날짜 없이 달력에 넣을 필요는 없다. 미정/보류를 올바르게 처리하는 것은 정상 동작이다. 반대로 공개된 확정 일정의 누락, 원천 오류를 무시한 성공 표시, 기존 데이터 재게시만 되는 신규 경로는 미완료다.

현재 근거: DATA74에서 영화/게임/EPL08:30 KST LaunchAgent 등록·명시OS기동3회/당일9skip,제어된 원천실패 격리·마지막 성공 보존·정상9범위 복구를 확인했다. 다음 자연08:30 기동은 미관측이다. 실제 게임29924(이번신규10)/EPL760/영화1909/OTT93,기존32683행·ID·이력 보존/신규10 공식대조·상세200/API30125 DB일치/자체331·일회용DB 재시도 검증. IGDB선택49건은29게임·기존5ID를 찾아37날짜후보/4부분·미정/3복수·부재/5현재비본편·가능중복38로 분류했다. 원래 숫자지역 미보존으로 동일 이벤트를 확정하거나 자동 재결속하지 않았다. 원천지역provenance·미검증/중복 게시와 공용ID·찜/alias 처리,미정 게임,OTT새시즌·나머지 원천 일반 자동검토/TMDB는 남는다. ## 2단계 · 배포 환경 설정·실제 배포

데이터 단계가 끝나면 디자인이나 새 기능 확장으로 옮기지 않고 배포 설정부터 진행한다. 기존 선택인 Render API와 Supabase PostgreSQL 방향을 유지하되 실행 시 실제 무료 플랜/비용·현재 이용 조건을 확인한다.

- [ ] 배포 설정·DB 연결/마이그레이션·비밀 환경변수·수집 실행 위치와 스케줄을 준비한다.
- [ ] 실제 클라우드에 실데이터를 반영하고 HTTPS health/일정API/갱신을 확인한다. 로컬93건이 원격에도 있다고 가정하지 않는다.
- [ ] iPhone 앱의 API주소·인증 설정·설치 연결을 준비하고 실제 원격 조회를 확인한다.
- [ ] 실패 로그·마지막 성공 확인·재실행 및 기본 복구 절차를 확인한다.

배포 설정 파일을 작성한 것과 실제 원격 배포가 성공한 것을 구분한다. 이번 우선순위 변경 자체로 외부 가입·결제·push·배포가 실행된 것은 아니다. 구체적인 원격 작업은 해당 단계의 사용자 지시·기존 권한 범위와 무료 우선 정책에 따라 진행한다.

## 3단계 · 기본기능 완료

월간 달력/날짜순 목록/상세/필터, Google 로그인·세션 복원·로그아웃, 계정 설정 저장·복원, 작품/일정 찜, 계정 전환, 실패·오프라인의 마지막 데이터/재시도 흐름을 실제 API/DB/iPhone 조합으로 확인한다.

APP-AUTH-13의 합성15개 성공과 빌드, BE-AUTH-07의 일회용DB 동시성 검사는 기존 근거로 유지하되 실제 Google 로그인·배포 서버·실폰 왕복 검증을 대신하지 않는다. 신규 기능을 늘리지 않고 V1 기본기능의 결함과 빈 사용 경로를 끝낸다.

## 4단계 · 디테일·디자인

기본기능 완료 후 배치·정보 위계·여백·타이포·상태 표현·이미지 표시와 사용성 정리를 진행한다. 기능 사용을 막는 문제의 수정은 해당 기본기능 작업으로 처리하고, 시각적 완성도를 이유로 앞 단계의 데이터/배포 검증을 미루지 않는다.

## 완료율 기록 원칙

단계별 필수 조건과 실제 증거로 완료/미완료를 표시한다. 전체70% 같은 추정치를 데이터 수집률이나 검증된 완료율로 재사용하지 않는다. 개발 완료 체크리스트와 독립 승인/제품 통합PASS는 별개이며 acceptance/verdict는 해당 원본과 절차를 유지한다.
