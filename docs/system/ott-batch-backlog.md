## 한 번의 배치 처리 절차

1. 원천/플랫폼별 후보를 모으고 안정ID와 시장·서비스·공개 방식·날짜 정밀도로 검토한다. 미확인은 사유/필요 근거를 남겨 배치에서 제외한다.
2. 전체 대상의 현재 revision·고정키·중복/identity·지원 유형을 DB 쓰기 전에 검증한다. 기준을 통과시키려고 기존 분류·날짜·verdict를 바꾸지 않는다.
3. 준비된 전체 매핑으로 기존 publish CLI를 한 번 실행한다. 쓰기 범위와 scope별 실패를 기록하고 같은 키로 재실행해 중복/변경이력 증가를 검사한다.
4. SQL/API에서 범위·건수뿐 아니라 예상ID·날짜·플랫폼·정밀도·기존행 불변을 확인한다. 작품 수, source별 staging 수, 실제 이벤트 수를 섞지 않는다.
5. 배치 작업을 종료하고 제품 기능 작업으로 돌아간다. 추가 후보가 있다는 이유로 사용자 ‘다음 작업’을 다시 데이터 적재로 해석하지 않는다.

기존 관측 원본: DATA-47~52 및 해당 data/reference/curated 파일. 현재 제품 작업 우선순위는 plan.md. 원본 카드/과거 실패는 삭제하지 않는다.
